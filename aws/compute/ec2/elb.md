Elastic Load Balancing (ELB) Overview
Introduction to Load Balancing
Let us learn about load balancing. You may ask, what is load balancing? A load balancer is a server or a set of servers that forward received traffic to multiple backend or downstream EC2 instances or servers.

For example, consider three EC2 instances fronted by an Elastic Load Balancer, which is a set of servers behind the scenes. When three users connect directly to your Elastic Load Balancer, the first user's load is sent to one backend EC2 instance. Because of load balancing, if another user connects, the traffic is sent to a different EC2 instance. Similarly, the third user will be load balanced and sent to the third EC2 instance. The idea is that as the number of users increases, the load is balanced across EC2 instances.

Users do not know which backend instances they are connected to; they only connect to the Elastic Load Balancer, which provides a single endpoint for connectivity.

Benefits of Using a Load Balancer
Using a load balancer to spread load across multiple downstream instances offers several advantages:

It exposes a single point of access to your applications.
It seamlessly handles failures of downstream instances through health check mechanisms that determine which instances can receive traffic.
It supports health checks on your instances.
It provides SSL termination, enabling HTTPS encrypted traffic for your websites.
It can enforce stickiness with cookies.
It ensures high availability across zones.
It separates public traffic from private traffic on your cloud.
Elastic Load Balancer as a Managed Service
The Elastic Load Balancer is a managed load balancer. AWS manages it and guarantees its operation under all circumstances. AWS handles upgrades, maintenance, and high availability. It also provides configuration options to tweak the load balancer's behavior.

Using an Elastic Load Balancer is cost-effective compared to setting up your own load balancer. Managing your own load balancer can be a nightmare from a scalability perspective. The Elastic Load Balancer integrates with many AWS services, including EC2 instances, scaling groups, Amazon ECS, Certificate Manager, CloudWatch, Route 53, WAF, Global Accelerator, and more over time. Therefore, using the Elastic Load Balancer is a straightforward choice for load balancing on AWS.

Health Checks
Health checks allow your Elastic Load Balancer to verify whether an EC2 instance is functioning properly. If an instance is unhealthy, the load balancer will not send traffic to it. Health checks are performed using a port and a route to check the health endpoint. For example, the protocol might be HTTP, the port 4567, and the endpoint /health. This route provides an easy way for the application to report its health status. If the EC2 instance does not respond with an OK response, usually the HTTP 200 status code, it is marked as unhealthy and excluded from receiving traffic.

Types of Managed Load Balancers on AWS
There are four kinds of managed load balancers on AWS:

Classic Load Balancer (CLB): The older generation from 2009, compatible with HTTP, HTTPS, TCP, SSL, and Security CP. AWS recommends not using it anymore; it is deprecated in the console but still available.
Application Load Balancer (ALB): Introduced around 2016, supports HTTP, HTTPS, and WebSocket protocols.
Network Load Balancer (NLB): Introduced in 2017, supports TCP, TLS, Security CP, and UDP protocols.
Gateway Load Balancer (GWLB): Introduced in 2020, operates at the network layer and supports the IP protocol.
It is recommended to use the newer generation load balancers as they provide more features.

Load balancers can be configured as internal (private) for private network access or external (public) for websites and public applications.

Security Considerations
Users can access your load balancer from anywhere using HTTP or HTTPS. Therefore, the security group rule for the load balancer typically allows inbound traffic on ports 80 or 443 from source 0.0.0.0/0, meaning anywhere. However, EC2 instances should only allow traffic coming directly from the load balancer. Thus, the security group rule for EC2 instances allows HTTP traffic on port 80, but the source is set to the security group of the load balancer. This links the EC2 instance's security group to the load balancer's security group, ensuring that the EC2 instance only accepts traffic originating from the load balancer, enhancing security.

Conclusion
This overview covered the essentials of load balancers. In subsequent sections, we will discuss classic, application, and network load balancers in more detail.

Key Takeaways
Load balancers distribute incoming traffic across multiple backend EC2 instances to optimize resource use and improve fault tolerance.
Elastic Load Balancers provide a single endpoint for users, hiding the complexity of backend instances.
Health checks enable the load balancer to route traffic only to healthy instances, enhancing reliability.
AWS offers multiple types of managed load balancers, with newer generations recommended for advanced features and better integration.

Elastic Load Balancer - Sticky Sessions
Introduction to Sticky Sessions
Let's talk about sticky sessions, also known as session affinity, for your Elastic Load Balancer (ELB).

Sticky sessions allow a client making multiple requests to the load balancer to be routed to the same backend instance each time. For example, if you have an Application Load Balancer (ALB) with two EC2 instances and three clients, client one making a request might be routed to the first EC2 instance. When client one makes a second request, it will be routed to the same instance. This behavior differs from the usual load balancer behavior, which spreads requests across all EC2 instances.

Similarly, client two might be routed to the second instance for all its requests, and the same applies to client three. Sticky sessions can be enabled for Classic Load Balancer (CLB), Application Load Balancer (ALB), and Network Load Balancer (NLB).

How Sticky Sessions Work
Sticky sessions work by sending a cookie as part of the request from the client to the load balancer. This cookie contains stickiness information and has an expiration date. When the cookie expires, the client may be redirected to a different EC2 instance.

The main use case for sticky sessions is to ensure that a user remains connected to the same backend instance, preventing loss of session data such as user login information. However, enabling stickiness can cause load imbalance across backend EC2 instances if some instances have very sticky users.

Types of Cookies for Sticky Sessions
There are two types of cookies used for sticky sessions:

Application-based cookies
Duration-based cookies
Application-Based Cookies
Application-based cookies are custom cookies generated by the target application itself. You can include any custom attributes required by your application. The cookie name must be specified individually for each target group. However, you must not use the following reserved names: AWSALB, AWSALBAPP, or AWSALBTG, as these are reserved for use by the ELB itself.

Duration-Based Cookies
Duration-based cookies are generated by the load balancer. For the ALB, the cookie name is AWSALB; for the CLB, it is AWSELB. These cookies have an expiration based on a specific duration set by the load balancer. In contrast, application-based cookies have durations specified by the application itself.

You do not need to memorize the exact cookie names or the details of custom versus application cookies, but remember that there are application-based cookies and duration-based cookies, each with specific names. This distinction will be important when discussing CloudFront.

Enabling Sticky Sessions on the Load Balancer
To enable sticky sessions, navigate to your load balancer and open it in a new tab. Initially, requests will be distributed among your instances. To enable stickiness, go to the target group level, open your target group, then select "Actions" and choose to edit the attributes of the target group.

Scroll down to the target selection configuration, where you will find the stickiness option. You can turn stickiness on and choose between two types:

Load balancer generated cookie
Application-based cookie
For the load balancer generated cookie, you can set a duration between one second and seven days. For the application-based cookie, you need to specify an application cookie name, for example, MYCUSTOMCOOKIEAPP. This name helps you identify how stickiness is applied at the load balancer level.

To keep things simple, choose the load balancer generated cookie with the default duration of one day, then save the changes.

Observing Sticky Sessions in Action
Open the developer tools in your browser and navigate to the Network tab. Refresh the page multiple times. You will notice that the requests are consistently routed to the same instance, for example, instance 7176 repeatedly responds.

Inspecting the GET request made to the load balancer, look at the Cookies section. You will see a response cookie indicating the cookie's expiration date, path, and value. The browser sends this cookie back in subsequent requests, enabling stickiness.

This cookie exchange is how sticky sessions work, maintaining session affinity between the client and the backend instance.

Additional Notes
To access web developer tools, click on "Web Developer" and then "Web Developer Tools". This shortcut works similarly on Chrome and Firefox. Navigate to the Network tab to view request information.

Finally, to disable stickiness and return to normal load balancing behavior, go back to your target group, edit the attributes, and disable stickiness.

That concludes this lecture on sticky sessions. I hope you found it informative.

Key Takeaways
Sticky sessions, or session affinity, ensure that a client’s requests are consistently routed to the same backend instance.
Sticky sessions can be enabled on Classic Load Balancer, Application Load Balancer, and Network Load Balancer using cookies.
There are two types of cookies for stickiness: application-based cookies generated by the target application, and duration-based cookies generated by the load balancer.
Enabling stickiness may cause load imbalance if some users have very sticky sessions.

Elastic Load Balancer - Cross Zone Load Balancing
Introduction to Cross Zone Load Balancing
Let us discuss cross zone balancing. Consider an example of a very imbalanced situation, which will help illustrate the point. Suppose there are two availability zones. The first one has a load balancer with two EC2 instances, and the second one also has a load balancer instance, but with eight EC2 instances. The load balancer instances are part of the same, more general load balancer. The client accesses these load balancers.

How Cross Zone Load Balancing Works
With cross zone load balancing, each load balancer instance distributes traffic evenly across all registered instances in all availability zones. For example, the client sends 50% of the traffic to the first Application Load Balancer (ALB) instance and 50% to the other ALB instance. Each ALB then redirects the traffic across all 10 EC2 instances, regardless of which availability zone they are in. This is why it is called cross zone load balancing.

If you look at the second ALB instance, it sends 10% of the traffic it receives to each of the 10 instances, because there are 10 instances in total. Each instance receives 10% of the traffic. The same applies to the first ALB instance. In this example, with cross zone balancing, traffic is distributed evenly across all EC2 instances. This behavior is available to you, and you may choose to use it or not.

Without Cross Zone Load Balancing
The second behavior available is to not have cross zone balancing. Using the same example but without cross zone balancing, the requests are distributed to the instances of the node of the elastic load balancer. In this case, the client sends 50% of the traffic to the first availability zone and 50% to the second. The first ALB instance sends traffic only to the EC2 instances in its own region. This means each EC2 instance in that availability zone receives 25% of the overall traffic, so half and half. The ALB instance on the right divides the traffic it receives among the EC2 instances registered within its availability zone.

Without cross zone balancing, traffic is contained within each availability zone. If there is an imbalanced number of EC2 instances in each availability zone, some EC2 instances in a specific zone will receive more traffic than others. This is simply an option to be aware of; there is no right or wrong answer, as it depends on the use case.

Default Settings and Charges for Different Load Balancers
For the Application Load Balancer, cross zone load balancing is enabled by default. You can disable it at the target group level. There are no charges if your data goes across availability zones, because usually in AWS, if data goes from one availability zone to another, you pay some money. However, for the Application Load Balancer, since cross zone load balancing is enabled by default, there are no charges for inter-availability zone data.

For the Network Load Balancer and the Gateway Load Balancer, cross zone load balancing is disabled by default. If you enable it, you will pay some amount because the data will go from one availability zone to the next. For the Classic Load Balancer, it is disabled by default, but if you enable it, you are not charged for inter-availability zone data transfers.

Demonstration of Load Balancer Settings
For demonstration, a Network Load Balancer, an Application Load Balancer, and a Gateway Load Balancer have been created. Looking at the Network Load Balancer, under attributes, cross zone load balancing is off by default, but it can be edited and turned on. Enabling cross zone balancing may include some regional charges for your Network Load Balancer. The Gateway Load Balancer has a similar setting and behavior. Under attributes, cross zone load balancing is off, but it can be edited and turned on, which will imply data charges.

For the Application Load Balancer, the setting is different. Under attributes, cross zone load balancing is on by default. If you edit and scroll down, you will see that cross zone balancing is always on. Any message to the contrary can be disregarded. Cross zone load balancing is always on for your Application Load Balancer.

If you go to the actual target group created for this, under attributes, you can edit the cross zone load balancing setting. You can either inherit settings from the load balancer attributes (which is on by default), force it on, or turn it off for that specific target group.

Classic Load Balancer and Final Notes
The Classic Load Balancer is not included in the demonstration because it is being retired. It is a previous generation and will be retired very soon, so it is not necessary to know about it for the exam.

For this lecture, if you followed along, remember to delete the load balancers. Thank you for your attention.

Key Takeaways
Cross zone load balancing distributes traffic evenly across all registered EC2 instances in all availability zones.
Without cross zone load balancing, traffic is distributed only within each availability zone, potentially causing imbalance if EC2 instance counts differ.
Application Load Balancer enables cross zone load balancing by default with no inter-AZ data charges, while Network and Gateway Load Balancers have it disabled by default and may incur charges if enabled.
Classic Load Balancer is being retired and is not recommended for new deployments.

Elastic Load Balancer - SSL Certificates
Introduction to SSL and TLS Certificates
This lecture covers the basics of SSL and TLS certificates. While the topic is complex, the goal is to introduce the core concepts clearly. Even if you are familiar with SSL and TLS, this lecture provides valuable insights, including details about Server Name Indication (SNI) and integration with load balancers.

An SSL certificate allows the traffic between your clients and your load balancer to be encrypted while in transit. This is known as in-flight encryption, meaning the data traveling through the network is encrypted and can only be decrypted by the sender and the receiver.

SSL stands for Secure Sockets Layer and is used to encrypt transfer connections. TLS, which stands for Transport Layer Security, is the newer version of SSL. Nowadays, TLS certificates are mainly used, but many people, including myself, still refer to them as SSL certificates for simplicity.

Public SSL certificates are issued by Certificate Authorities such as Comodo, Symantec, GoDaddy, GlobalSign, Digicert, and Letsencrypt. By attaching a public SSL certificate to our load balancer, we can encrypt the connection between clients and the load balancer.

When you visit a website like google.com and see a lock or green lock icon, it means your traffic is encrypted. If the traffic is not encrypted, you will see a warning indicating the connection is not secure, advising against entering sensitive information such as credit card details or login credentials.

SSL certificates have an expiration date and must be renewed regularly to ensure authenticity.

SSL Certificates and Load Balancers
From a load balancer perspective, users connect over HTTPS, which uses SSL certificates to encrypt the connection. The connection is secure over the public internet to your load balancer.

Internally, the load balancer performs SSL certificate termination. It decrypts the incoming encrypted traffic and can communicate with backend EC2 instances using HTTP, which is not encrypted. However, this traffic flows within your Virtual Private Cloud (VPC), a private network, providing a degree of security.

The load balancer loads an X.509 certificate, also known as an SSL or TLS server certificate. In AWS, you can manage these certificates using AWS Certificate Manager (ACM). You can also upload your own certificates to ACM if desired.

When setting up an HTTPS listener on the load balancer, you must specify a default certificate. Additionally, you can add an optional list of certificates to support multiple domains. Clients can use Server Name Indication (SNI) to specify the hostname they are reaching.

You can also set a specific security policy for HTTPS to support various versions of SSL and TLS, including legacy clients.

Understanding Server Name Indication (SNI)
SNI solves the important problem of how to load multiple SSL certificates onto one web server so that it can serve multiple websites. It is a newer protocol that requires the client to indicate the hostname of the target server during the initial SSL handshake.

During the handshake, the client specifies the website it wants to connect to. The server then knows which SSL certificate to load based on this information. This protocol is relatively new and not all clients support it.

SNI works with Application Load Balancers (ALB), Network Load Balancers (NLB), and CloudFront, but it does not work with Classic Load Balancers because they are older generation.

Whenever you see multiple SSL certificates on your load balancer, it is likely an ALB or NLB.

Diagram of SNI with ALB
Consider an Application Load Balancer (ALB) with two target groups: www.mycorp.com and Domain1.example.com. The ALB routes traffic to these target groups based on rules, such as the hostname.

The ALB holds two SSL certificates corresponding to the two domains. When a client connects and requests www.mycorp.com, the ALB uses SNI to identify the requested hostname and selects the correct SSL certificate to encrypt the traffic.

The ALB then routes the request to the appropriate target group, www.mycorp.com. Similarly, if a client requests Domain1.example.com, the ALB selects the corresponding SSL certificate and routes to the Domain1.example.com target group.

Using SNI, you can have multiple target groups for different websites, each using different SSL certificates.

SSL Certificate Support Across Load Balancer Types
Classic Load Balancer supports only one SSL certificate. To support multiple hostnames with multiple SSL certificates, you need to use multiple Classic Load Balancers.
Application Load Balancer (ALB) version 2 supports multiple listeners with multiple SSL certificates using SNI.
Network Load Balancer (NLB) also supports multiple listeners with multiple SSL certificates using SNI.
Key Takeaways
SSL certificates enable encrypted traffic between clients and load balancers, ensuring secure in-flight data transmission.
TLS is the modern version of SSL, but the term SSL is still commonly used for simplicity.
Server Name Indication (SNI) allows multiple SSL certificates to be hosted on a single load balancer, enabling support for multiple domains.
Application Load Balancers (ALB) and Network Load Balancers (NLB) support multiple SSL certificates with SNI, whereas Classic Load Balancers support only one SSL certificate.

Elastic Load Balancer - Connection Draining
Introduction to Connection Draining
Connection Draining is a feature relevant for load balancers, which may appear in exams. It is known by two names depending on the type of load balancer used.

For Classic Load Balancers, it is called Connection Draining.
For Application Load Balancers and Network Load Balancers, it is referred to as Deregistration Delay.
The core idea behind this concept is to provide time for instances to complete inflight or active requests while they are being deregistered or marked unhealthy.

Once an instance is in the draining state, the Elastic Load Balancer (ELB) stops sending new requests to that EC2 instance while it is being deregistered.

Understanding Connection Draining with a Diagram
Consider a scenario with three EC2 instances behind a load balancer. When one instance is set to draining mode, users already connected to that instance are allowed enough time, known as the draining period, to complete their existing connections and requests.

After all active connections finish, the connections are shut down. Meanwhile, new users attempting to connect to the ELB will be routed only to the other healthy EC2 instances that are not in draining state.

Configuring Connection Draining Parameters
The Connection Draining period can be configured between 1 and 3,600 seconds. By default, it is set to 300 seconds, which equals five minutes.

You can also disable Connection Draining altogether by setting the value to zero, which means no draining will occur.

If your requests are very short, for example less than one second, it is advisable to set the draining period to a low value such as 30 seconds. This allows the EC2 instance to be drained quickly and taken offline or replaced as needed.

Conversely, if your requests are long-lived, such as uploads or extended sessions, you should set the draining period to a higher value. The trade-off is that the EC2 instance will remain online longer until the draining period completes.

Summary
Connection Draining or Deregistration Delay is an important feature to ensure graceful handling of active connections during instance deregistration. Proper configuration depends on the nature of your requests and desired instance replacement timing.

Key Takeaways
Connection Draining is a feature that allows instances to complete active requests before deregistration.
It is called Connection Draining in Classic Load Balancers and Deregistration Delay in Application and Network Load Balancers.
The draining period can be configured between 1 and 3600 seconds, with a default of 300 seconds.
Setting a low draining time is suitable for short requests, while longer draining times accommodate long-lived requests but delay instance removal.
