# AWS AppConfig Cheat Sheet

**AWS AppConfig** ช่วยให้นักพัฒนาซอฟต์แวร์สามารถปรับเปลี่ยนพฤติกรรมของแอปพลิเคชันในสภาพแวดล้อมจริง (Production) ได้อย่างรวดเร็วและปลอดภัย โดยไม่จำเป็นต้อง Deploy โค้ดใหม่ ช่วยเพิ่มความถี่ในการปล่อยซอฟต์แวร์ เสริมความยืดหยุ่นของแอปพลิเคชัน และตอบสนองต่อปัญหาที่เกิดขึ้นได้อย่างรวดเร็ว

### คุณสมบัติหลัก (Key Features)
* **Feature Flags:** ช่วยในการค่อยๆ ปล่อยคุณสมบัติใหม่ให้ผู้ใช้ และวัดผลกระทบของการเปลี่ยนแปลงก่อนจะเปิดใช้งานเต็มรูปแบบ
* **Dynamic Configurations:** เปิดใช้งานการอัปเดต Block lists, Allow lists, การจำกัด Throttling, รายละเอียดการทำ Log และการปรับแต่งการดำเนินงานอื่นๆ เพื่อตอบสนองต่อปัญหาใน Production ได้ทันที
* **Validators:** ตรวจสอบข้อมูลการตั้งค่าให้ถูกต้องทั้งตามไวยากรณ์ (Syntactic) และความหมาย (Semantic) ก่อนที่จะนำการเปลี่ยนแปลงไปใช้จริง
* **Deployment Strategies:** ช่วยให้การปล่อยการเปลี่ยนแปลงสู่ Production เป็นไปอย่างช้าๆ โดยใช้เวลาเป็นนาทีหรือชั่วโมง
* **Multi-target Deployment:** Deploy การตั้งค่าไปยัง EC2, Lambda, ECS, อุปกรณ์ IoT หรือโมบายแอปได้พร้อมกัน
* **การตรวจสอบและการ Rollback อัตโนมัติ:** ทำงานร่วมกับ **Amazon CloudWatch** เพื่อเฝ้าติดตามการเปลี่ยนแปลง หากการตั้งค่าก่อให้เกิด Alarm ใน CloudWatch ระบบจะทำการ Rollback (ย้อนกลับ) การตั้งค่าโดยอัตโนมัติเพื่อรักษาความสมบูรณ์ของแอปพลิเคชัน

### ประโยชน์ (Benefits)
* **ลดการหยุดชะงักของระบบที่คาดไม่ถึง:** ช่วยลด Downtime โดยการสร้างกฎเพื่อตรวจสอบความถูกต้อง (Validation) ก่อนการ Deploy ซึ่ง AppConfig มี 2 วิธีหลักคือ:
    * **Syntactic validation:** ตรวจสอบโครงสร้างไวยากรณ์ (เช่น ใช้ JSON Schema)
    * **Semantic validation:** ตรวจสอบความหมายของข้อมูล (เช่น เรียกใช้ AWS Lambda เพื่อตรวจสอบตรรกะภายในข้อมูลการตั้งค่า)
* **Deploy การเปลี่ยนแปลงไปยังเป้าหมายจำนวนมากได้อย่างรวดเร็ว:** จัดการแอปพลิเคชันขนาดใหญ่ได้จากจุดศูนย์กลาง โดยสามารถเก็บการตั้งค่าไว้ใน AppConfig Hosted Store, Parameter Store, SSM Documents หรือ Amazon S3
* **อัปเดตแอปพลิเคชันโดยไม่ขัดจังหวะการทำงาน:** ปรับเปลี่ยนการตั้งค่าไปยังเป้าหมายได้ในขณะที่ระบบกำลังทำงานอยู่ ไม่ต้องผ่านกระบวนการ Build ที่ซับซ้อน หรือต้องเอาเครื่องออกจากระบบ (Out of service)
* **ควบคุมความเสี่ยงในการ Deploy:** ใช้กลยุทธ์การ Deploy (Deployment Strategy) เพื่อค่อยๆ ปล่อยการเปลี่ยนแปลงไปยังกลุ่มโฮสต์ (Fleet) หากพบปัญหา สามารถย้อนกลับการตั้งค่าได้ทันทีก่อนที่จะส่งผลกระทบต่อโฮสต์ส่วนใหญ่
* **การตรวจสอบและเวอร์ชัน (Audit & Versioning):** ติดตามประวัติการ Deploy แยกตามเวอร์ชัน เพื่อความสอดคล้องตามข้อกำหนด (Compliance) หรือการแก้ไขปัญหา
* **การควบคุมเฉพาะสภาพแวดล้อม:** ลดความเสี่ยงโดยใช้การเปลี่ยนแปลงเฉพาะกับสภาพแวดล้อมที่ตั้งใจไว้เท่านั้น (เช่น Dev, Test, Prod)
