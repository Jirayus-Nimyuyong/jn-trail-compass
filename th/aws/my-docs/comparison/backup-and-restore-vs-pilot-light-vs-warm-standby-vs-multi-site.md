### **1. Backup and Restore (การสำรองและกู้คืนข้อมูล)**
* เป็นแผน DR ที่มี **การกู้คืนระบบช้าที่สุด** หลังจากเกิดเหตุการณ์ภัยพิบัติ
* ใช้วิธีการทำ Snapshot ข้อมูลบ่อย ๆ เช่น ข้อมูลใน Amazon EBS Volumes และฐานข้อมูล Amazon RDS แล้วนำไปเก็บไว้ในที่จัดเก็บที่ทนทานและปลอดภัยอย่าง Amazon S3
* **การเคลื่อนย้ายข้อมูลเข้า-ออก S3 ทำได้หลายวิธี:**
    * ส่งผ่านเครือข่ายด้วย S3 Transfer Acceleration
    * ส่งผ่านสายสัญญาณเฉพาะด้วย AWS Direct Connect
    * ส่งโดยใช้ฮาร์ดแวร์เคลื่อนย้ายข้อมูล เช่น AWS Snowball Edge และ Snowmobile
* การใช้ **S3 Glacier** ช่วยลดค่าใช้จ่ายได้มหาศาลเมื่อเทียบกับ S3 Standard เพราะออกแบบมาสำหรับการเก็บข้อมูลระยะยาวซึ่งเหมาะกับการทำ Backup
* **AWS Storage Gateway** ช่วยให้สามารถคัดลอก Snapshot ของ Volume ข้อมูลจาก On-premises ไปยัง S3 ได้อย่างราบรื่น
    * *Storage-cached volumes:* เก็บข้อมูลหลักไว้บน S3 แต่เก็บข้อมูลที่ใช้บ่อยไว้ในเครื่องเพื่อความเร็ว (Low-latency)
    * *Gateway-VTL:* ใช้แทนการสำรองข้อมูลด้วยเทปแม่เหล็กแบบดั้งเดิม
* คุณสามารถสร้าง Local volumes หรือ Amazon EBS volumes จาก Snapshot ใน S3 ได้อย่างรวดเร็ว
* คุณสามารถสร้าง **AMIs** จากอินสแตนซ์ EC2 ซึ่งจะเก็บข้อมูลดังนี้:
    * เทมเพลตสำหรับ Root volume (เช่น ระบบปฏิบัติการ, แอปพลิเคชันเซิร์ฟเวอร์ และแอปพลิเคชันต่างๆ)
    * สิทธิ์การเรียกใช้งาน (Launch permissions) ว่าบัญชี AWS ใดสามารถใช้อันนี้ได้บ้าง
    * การจับคู่ Block device (Block device mapping) เพื่อระบุ Volume ที่ต้องติดตั้งเมื่อเปิดเครื่อง
* วิธี Backup and restore มักใช้ควบคู่กับแผน DR อื่น ๆ เพราะการมีตัวสำรองที่ใช้งานได้เสมอถือเป็นเรื่องวิกฤต

### **2. Pilot Light (ดวงไฟนำทาง)**
* ให้เวลาในการกู้คืน (Recovery Time) **เร็วกว่า** วิธี Backup and Restore เพราะส่วนประกอบหลักของระบบรันอยู่แล้วและอัปเดตตลอดเวลา แต่ไม่เร็วเท่าวิธี Warm Standby
* ทำได้โดยการกำหนดค่าและรัน **องค์ประกอบหลักที่สำคัญที่สุด (Most critical core elements)** ของระบบไว้บน AWS เมื่อถึงเวลาต้องกู้คืน คุณจะสามารถจัดเตรียมสภาพแวดล้อมการผลิตเต็มรูปแบบรอบ ๆ แกนหลักที่สำคัญนั้นได้อย่างรวดเร็ว
* เป็นตัวอย่างของการกำหนดค่าแบบ **Active/Passive Failover**
* โดยทั่วไปองค์ประกอบหลักที่รันไว้ใน Pilot Light คือ **เซิร์ฟเวอร์ฐานข้อมูล** ซึ่งจะถูกตั้งค่าให้ทำ Data Mirroring Replication (การคัดลอกข้อมูลเสมือนกระจกเงา)
* การกู้คืนส่วนที่เหลือของระบบจะใช้ประโยชน์จาก EBS Snapshots และ EC2 AMIs ที่คุณต้องสร้างไว้อย่างสม่ำเสมอ
* ค่าใช้จ่ายสูงกว่า Backup and Restore เล็กน้อย เพราะต้องรันทรัพยากรหลักบางอย่างทิ้งไว้ตลอดเวลา
* **ในมุมมองของเครือข่าย มี 2 ทางเลือกหลักในการจัดเตรียมเว็บเซิร์ฟเวอร์:**
    1.  ใช้ **Elastic IP addresses** ที่จองไว้ล่วงหน้าเพื่อผูกกับอินสแตนซ์ใหม่
    2.  ใช้ **Elastic Load Balancing (ELB)** และอัปเดตระเบียน DNS ให้ชี้ไปที่อินสแตนซ์หรือ Load Balancer โดยใช้ CNAME
* หากมีการเปลี่ยนแปลงข้อมูลตลอดเวลาและเกิด Failover คุณจะต้องทำ **Reverse Replicate** ข้อมูลจากไซต์ DR กลับไปยังไซต์หลัก เพื่อให้ข้อมูลที่อัปเดตตอนไซต์หลักล่มถูกส่งกลับไปได้โดยไม่มีข้อมูลสูญหาย

### **3. Warm Standby (สแตนด์บายแบบพร้อมใช้)**
* การกู้คืนระบบ **เร็วกว่า Pilot Light** แต่ไม่เร็วเท่าวิธี Multi-site
* คือสถานการณ์ที่สภาพแวดล้อมที่ใช้งานได้จริงแต่เป็น **เวอร์ชันลดขนาด (Scaled-down version)** รันอยู่บนคลาวด์ตลอดเวลา
* เนื่องจากไม่ใช่แค่ส่วนประกอบหลักเท่านั้นที่รันอยู่ ทำให้ Warm Standby มักจะมี **ค่าใช้จ่ายสูงกว่า Pilot Light**
* เป็นอีกหนึ่งตัวอย่างของการกำหนดค่าแบบ **Active/Passive Failover**
* เซิร์ฟเวอร์จะรันอยู่ในรูปแบบ EC2 จำนวนน้อยที่สุดและขนาดเล็กที่สุดเท่าที่จะทำได้ เมื่อเกิด Failover ให้รีบขยายขนาด (Resize) และเพิ่มขีดความสามารถในการสเกล (Scaling) โดยควรวางอินสแตนซ์เหล่านี้ไว้หลัง Load Balancer
* ในส่วนของข้อมูล จะคล้ายกับ Pilot Light คือมีทรัพยากร Standby และข้อมูลที่มีการเปลี่ยนแปลงจะถูกคัดลอก (Replicate) ไปยังอีกฝั่งตลอดเวลา
* เมื่อระบบหลักล่ม สภาพแวดล้อม Standby จะถูกขยายขนาดขึ้น (Scale up) เพื่อรับโหลดการผลิต และระเบียน DNS จะถูกเปลี่ยนเพื่อส่งทราฟฟิกทั้งหมดมาที่ AWS
* ต้องทำ **Reverse Replicate** ข้อมูลกลับไปยังไซต์หลักเมื่อกู้คืนสำเร็จเช่นกัน เพื่อไม่ให้ข้อมูลสูญหาย

### **4. Multi-site (หลายไซต์ทำงานพร้อมกัน)**
* เป็นแผน DR ที่มี **การกู้คืนระบบเร็วที่สุด** ในบรรดาทุกวิธี
* เป็นการสำรองโครงสร้างพื้นฐานแบบ **หนึ่งต่อหนึ่ง (One-to-one copy)** ที่รันอยู่ในอีกภูมิภาคหรือ AZ หนึ่ง เรียกว่าการกำหนดค่าแบบ **Active-Active**
* ด้วยเหตุนี้ Multi-site จึงเป็นแผน DR ที่มี **ราคาแพงที่สุด**
* ให้ค่า RTO และ RPO ดีที่สุด เพราะคาดการณ์ว่าระบบจะ **ไม่มี Downtime** และแทบไม่มีข้อมูลสูญหายเลย
* มีวิธีการคัดลอกข้อมูลหลายแบบ ทั้งแบบ Synchronous (พร้อมกันทันที) และ Asynchronous (ไม่พร้อมกัน)
* ใช้บริการ DNS ที่รองรับ **Weighted Routing (การกำหนดน้ำหนักเส้นทาง)** เช่น Amazon Route 53 เพื่อส่งทราฟฟิกไปยังไซต์ต่าง ๆ ที่ให้บริการแอปพลิเคชันเดียวกัน
* ในระหว่าง Failover คุณสามารถเพิ่มขีดความสามารถในการประมวลผลได้อย่างรวดเร็วโดยใช้ AWS Auto Scaling หรือการเปลี่ยนขนาดอินสแตนซ์ให้ใหญ่ขึ้น
* บริการหลายอย่างเช่น RDS มีฟีเจอร์ Multi-AZ ที่ช่วยให้จัดเตรียมทรัพยากรไว้ในที่ต่างกันเพื่อความทนทานต่อความผิดพลาด (Fault-tolerant)
* หากเกิด Failover ต้องทำ **Reverse Replicate** ข้อมูลกลับไปยังไซต์หลักเพื่อให้ข้อมูลเป็นปัจจุบันและไม่มีข้อมูลสูญหาย
