# Redis Append-Only Files (AOF) และ การทำ Replication

### **Redis Append-Only Files (AOF)**
คุณสามารถเปิดใช้งานฟีเจอร์ **Append-Only File (AOF)** ของ Redis เพื่อความคงทนของข้อมูล (Data durability) ซึ่งคล้ายกับการทำ Backup ด้วยตนเอง เมื่อเปิดใช้งาน โหนดจะบันทึกคำสั่งทั้งหมดที่มีการเปลี่ยนแปลงข้อมูลในแคชลงในไฟล์ AOF

* **การกู้คืนข้อมูล:** เมื่อโหนดถูกรีบูตและ Engine เริ่มทำงาน Redis จะไล่ดูไฟล์ AOF เพื่อทำซ้ำ (Replay) คำสั่งที่เคยเกิดขึ้นก่อนที่ระบบจะขัดข้อง ผลลัพธ์คือจะได้ **Warm Redis Cache** ที่มีข้อมูลครบถ้วน
* **การตั้งค่า:** ต้องสร้าง Parameter Group โดยตั้งค่า `appendonly` เป็น `yes` และใช้พารามิเตอร์ `appendfsync` เพื่อควบคุมความถี่ในการเขียนข้อมูลลงไฟล์
* **ข้อจำกัด:** * หากใช้ Multi-AZ Replication จะ **ไม่สามารถ** เปิดใช้งาน AOF ได้ (ต้องเลือกอย่างใดอย่างหนึ่ง)
    * AOF ไม่สามารถป้องกันความล้มเหลวได้ทุกรูปแบบ เช่น หากฮาร์ดแวร์เซิร์ฟเวอร์หลักพัง ElastiCache จะจัดเตรียมโหนดใหม่บนเซิร์ฟเวอร์อื่น ซึ่งไฟล์ AOF เดิมจะหายไปและไม่สามารถกู้คืนได้ (กลายเป็น Cold Cache)
    * เนื่องจากเป็นไฟล์ อาจเกิดข้อผิดพลาด "พื้นที่ดิสก์เต็ม" ได้ AWS จึงแนะนำให้ใช้การทำ Replication ร่วมกับ Multi-AZ แทนเพื่อความน่าเชื่อถือที่สูงกว่า

**ข้อดีของ AOF:**
* เลือกนโยบาย `fsync` ได้หลากหลาย: ไม่ทำเลย, ทำทุกวินาที, หรือทำทุกคำคิวรี
* บันทึกข้อมูลแบบต่อท้ายไฟล์ (Append only) จึงไม่ต้องกังวลเรื่องการค้นหาตำแหน่ง (Seek) หรือไฟล์เสียหากไฟดับ
* Redis สามารถสั่ง **Rewrite** ไฟล์ AOF ใหม่ในเบื้องหลังโดยอัตโนมัติเมื่อไฟล์มีขนาดใหญ่เกินไป เพื่อให้ได้ไฟล์ที่มีชุดคำสั่งน้อยที่สุดแต่ได้ผลลัพธ์ข้อมูลเท่าเดิม
* ข้อมูลในไฟล์อ่านง่ายและวิเคราะห์ (Parse) ได้ง่าย

### **Redis Replication (การจำลองข้อมูล)**
Redis มีการทำ Replication 2 รูปแบบหลัก:

#### **1. Redis (Cluster Mode Disabled)**
* มีเพียง **ชาร์ดเดียว (Single Shard)** ที่เก็บข้อมูลทั้งหมดของคลัสเตอร์ไว้ในทุกโหนด (1 โหนดหลัก และโหนดรองสำหรับอ่านสูงสุด 5 โหนด)
* **ไม่สามารถ** แบ่งส่วนข้อมูล (Partition) ระหว่างโหนดได้
* ใช้กลไกการคัดลอกข้อมูลแบบไม่พร้อมกัน (**Asynchronous Replication**) เพื่อซิงค์ข้อมูลจากโหนดหลักไปยังโหนดรอง
* ทุกโหนดต้องอยู่ในภูมิภาค (Region) เดียวกัน แต่กระจายอยู่คนละ Availability Zone (AZ) ได้
* รองรับ **Multi-AZ with Automatic Failover** (หากไม่มีโหนดรองแล้วโหนดหลักพัง ข้อมูลจะสูญหายทั้งหมด)
* **เหมาะสำหรับ:** แอปพลิเคชันที่เน้นการอ่านข้อมูลปริมาณมหาศาลพร้อมกัน



#### **2. Redis (Cluster Mode Enabled)**
* ข้อมูลจะถูกแบ่งส่วน (Partitioned) กระจายไปตามชาร์ดต่างๆ ตั้งแต่ **1 ถึง 250 ชาร์ด** (หรือ 500 ชาร์ดในเวอร์ชัน 5.6.0 ขึ้นไป)
* โหนดรองในแต่ละชาร์ดจะเก็บสำเนาข้อมูลจากโหนดหลัก **เฉพาะของชาร์ดนั้นๆ**
* สามารถปรับเปลี่ยนจำนวนชาร์ดได้แบบไดนามิกเพื่อรองรับความต้องการ
* ใช้การคัดลอกข้อมูลแบบไม่พร้อมกัน (Asynchronous Replication) เช่นกัน
* **ข้อบังคับ:** ต้องเปิดใช้งาน **Multi-AZ with Automatic Failover** เสมอ
* หากชาร์ดใดไม่มีโหนดรองและโหนดหลักพัง ข้อมูลในชาร์ดนั้นจะสูญหายทั้งหมด
* **ไม่สามารถ** สั่งเลื่อนสถานะโหนดรองให้เป็นโหนดหลักด้วยตนเองได้ (ระบบจัดการอัตโนมัติ)
