# AWS Identity and Access Management (IAM) Cheat Sheet

**AWS Identity and Access Management (IAM)** เป็นบริการระดับโลก (Global Service) ที่ช่วยให้คุณจัดการการเข้าถึงบริการและทรัพยากรของ AWS ได้อย่างปลอดภัย โดยควบคุมทั้งการ **ยืนยันตัวตน** (Authentication - ใครที่ล็อกอินเข้าใช้) และการ **อนุญาตสิทธิ์** (Authorization - มีสิทธิ์ทำอะไรได้บ้าง)

### คุณสมบัติเด่น (Features)
* **บริการระดับโลก:** การตั้งค่า IAM มีผลกับทุกภูมิภาค (Regions) ของ AWS ทันที
* **การควบคุมสิทธิ์ที่ละเอียด:** อนุญาตให้กำหนดสิทธิ์เฉพาะเจาะจงถึงระดับทรัพยากร (เช่น อ่านไฟล์ใน S3 Bucket เฉพาะใบ) แทนที่จะให้สิทธิ์ทั้งบัญชี
* **Network Perimeter Controls:** ใช้เงื่อนไข (Condition Keys) เช่น `aws:VpceAccount` เพื่อบังคับให้การเรียกใช้งานต้องผ่าน VPC Endpoint ที่กำหนดเท่านั้น
* **IAM Access Analyzer:** ช่วยระบุว่าใคร (Principals) ภายในองค์กรที่มีสิทธิ์เข้าถึงทรัพยากรที่สำคัญ
* **การรองรับ Dual-Stack:** เข้าถึง IAM ได้ทั้งผ่าน IPv4 และ IPv6
* **Resource Control Policies (RCPs):** ฟีเจอร์ใหม่ของ AWS Organizations เพื่อจำกัดสิทธิ์สูงสุดภายในบัญชีหรือ OU

---

### อัตลักษณ์ของ IAM (IAM Identities)
1.  **Root User:** อัตลักษณ์แรกที่ถูกสร้างขึ้น มีสิทธิ์สูงสุดและไม่จำกัด **ควรเก็บรักษาให้ปลอดภัยและไม่ควรใช้ในงานประจำวัน**
2.  **IAM Users:** ข้อมูลประจำตัวระยะยาว (รหัสผ่าน/Access Keys) สำหรับบุคคลหรือระบบ (ปัจจุบันถือเป็นวิธีเก่าสำหรับมนุษย์ แนะนำให้ใช้ IAM Identity Center แทน)
3.  **IAM Groups:** กลุ่มของ User ที่ใช้เพื่อกำหนดสิทธิ์ให้กับคนจำนวนมากพร้อมกัน (Group ไม่ใช่อัตลักษณ์ คุณไม่สามารถล็อกอินในนามกลุ่มได้)
4.  **IAM Roles:** อัตลักษณ์ที่ **ไม่มีข้อมูลประจำตัวระยะยาว** โดยผู้ใช้งานจะทำการ "Assume" (สวมสิทธิ์) เพื่อรับข้อมูลประจำตัวชั่วคราวมาใช้งานในช่วงเวลาสั้นๆ
    * **Service-Linked Roles:** บทบาทที่ AWS กำหนดไว้เพื่อให้บริการต่างๆ ทำงานแทนคุณได้อย่างปลอดภัย

---

### นโยบาย (Policies/Permissions)
นโยบายเป็นเอกสาร **JSON** ที่กำหนด: **Effect** (Allow/Deny), **Action** (API ที่เรียกใช้), และ **Resource** (เป้าหมาย)

* **Identity-Based Policies:** ติดตั้งไว้ที่ User, Group หรือ Role เพื่อบอกว่าเขาทำอะไรได้บ้าง (มีทั้งแบบ Managed ที่ใช้ซ้ำได้ และ Inline ที่ฝังไว้กับตัวเลย)
* **Resource-Based Policies:** ติดตั้งไว้ที่ตัวทรัพยากรโดยตรง (เช่น S3 Bucket Policy) เพื่อบอกว่า "ใคร" บ้างที่เข้าถึงมันได้
* **Permissions Boundary:** ฟีเจอร์ขั้นสูงที่ใช้กำหนด "เพดานสิทธิ์สูงสุด" ที่อัตลักษณ์นั้นจะมีได้
* **ตรรกะการประเมินผล:**
    1.  **Explicit Deny (สั่งห้ามชัดเจน)** → บล็อกทันที
    2.  **Explicit Allow (อนุญาตชัดเจน)** → อนุญาตถ้าไม่มีคำสั่ง Deny
    3.  **Implicit Deny (ปฏิเสธโดยนัย)** → ถ้าไม่มีคำสั่ง Allow จะถูกปฏิเสธโดยค่าเริ่มต้น

### บริการที่เกี่ยวข้อง
* **AWS STS (Security Token Service):** บริการมอบข้อมูลประจำตัวชั่วคราว (เช่น `AssumeRole`)
* **IAM Identity Center (เดิมคือ AWS SSO):** มาตรฐานใหม่สำหรับการจัดการอัตลักษณ์ของพนักงาน จัดการสิทธิ์ข้ามหลายบัญชี AWS ได้จากที่เดียว
* **IAM Access Analyzer:** ตรวจสอบนโยบายล่วงหน้าและแนะนำแนวทางที่ปลอดภัย เพื่อป้องกันการแชร์ทรัพยากรออกสู่ภายนอกโดยไม่ตั้งใจ

---

### แนวทางปฏิบัติที่ดีที่สุด (Best Practices)
* **เก็บ Root ให้มิดชิด:** ลบ Access Keys ของ Root, เปิด MFA และใช้ Root เฉพาะตอนสร้าง Admin คนแรกเท่านั้น
* **หลักการสิทธิ์ขั้นต่ำ (Least Privilege):** ให้สิทธิ์เฉพาะที่จำเป็นต่องานนั้นๆ เท่านั้น
* **เปิดใช้งาน MFA:** บังคับใช้การยืนยันตัวตนหลายชั้นสำหรับทุกคน โดยเฉพาะ Admin
* **หมุนเวียน Access Keys:** เปลี่ยนคีย์สม่ำเสมอเพื่อลดความเสี่ยง
* **ใช้ Role สำหรับเครื่องคอมพิวเตอร์:** ห้ามเขียนรหัสผ่านทิ้งไว้ในโค้ด (Hard-code) ให้ใช้ IAM Role สำหรับ EC2 หรือ Lambda แทน

---

### กรณีการใช้งาน (Use Cases)
1.  **EC2 เข้าถึง S3:** สร้าง IAM Role ที่มีสิทธิ์ S3 แล้วติดตั้งเข้ากับ EC2 (Instance Profile) เพื่อให้แอปดึงข้อมูลได้โดยไม่ต้องเก็บ Access Key ไว้ในเครื่อง
2.  **การเข้าถึงข้ามบัญชี:** นักพัฒนาในบัญชี A สามารถ Assume Role เข้าไปจัดการฐานข้อมูลในบัญชี B ได้โดยไม่ต้องสร้าง User ใหม่ในบัญชี B
3.  **แอปมือถือ:** ผู้ใช้ล็อกอินผ่าน Facebook/Google แล้วใช้ Cognito เพื่อแลกเปลี่ยน Token เป็นสิทธิ์ AWS ชั่วคราวผ่าน STS
